Inside and outside

One tool for what used to take two

An agent on every machine reports what happens inside it. Checks look at your services from outside, from the hub and from probes in other places. Both meet in one view, with one set of alerts.

Machines

CPU, load, memory and swap, disks and their I/O, network, I/O wait and steal, uptime and reboots. systemd units that failed, and updates that wait for a restart.

Containers

Every Docker container with its status, health, restarts, CPU, memory and network. A container that stops or turns unhealthy shows up the moment Docker says so.

Checks

HTTP with any method, headers and body, held to a status, a keyword, a JSON value or a response time; TLS certificates, TCP ports, DNS records, domain expiry, and heartbeats for cron jobs and backups that must call in.

Probes

Checks run from the hub and from probes in other places. A check is down when most of them agree, so one network's bad minute wakes no one.

Alerts

Alerts that say why

Every alert shows the rule that fired, the values that made it fire, and what happened before. The rules are on from the start.

  • Calm by design. A condition must hold for a while before it fires and clear for a while before it ends, so nothing flaps.
  • Silence is an alert. A machine or a probe that stops reporting is not “fine”; it is a problem of its own.
  • Where you are. Email, Slack, Discord, Google Chat, Telegram, ntfy, Pushover or any webhook, routed per customer or project.
  • Maintenance windows, acknowledgements, and a dead man's switch that tells you when the hub itself goes quiet.

Customers and projects

Built for the machines of many

Machines and checks live in customers, projects and environments. Settings are made once, high up, and hold for everything below, unless something below says otherwise.

  • Inherited, and shown so. Every machine and check shows the value that applies to it and where it comes from.
  • A history for everything. Who changed what, when, and how: in the interface, from a file, or through a container's labels.
  • Each customer their own channel. Alerts follow the hierarchy, so one customer's problems reach that customer's people.

Configuration

Click it, write it, or label it

There is one configuration, in the hub's database, and three ways to change it. Use whichever fits; they all end up in the same place.

In the interface

Everything can be done here, with forms that explain themselves. Adding a machine is one line to copy.

As code

lotse apply takes a lotse.yaml from Git or your deploy pipeline. --dry-run shows the difference first; lotse export writes what is there as a file.

With Docker labels

A container brings its own checks, the way Traefik routes: lotse.check.web.http.url next to the service it watches.

Getting started

Running in a few minutes

No configuration is needed before the first chart appears.

Start the hub

On a machine with Docker. It prints a link; the first login there becomes the admin.

curl -fsSL https://lotse.sh/install | sudo sh -s -- hub

Add a customer

A customer, a project and an environment: three fields. Then Add host shows the line for your machine, token included.

Run the line

The machine and its containers appear within seconds, with the default alerts already on.

curl -fsSL https://lotse.sh/install | sudo sh -s -- agent --hub https://… --token …

Small and safe

Few moving parts, and none pointing in

One binary

Hub, agent and probe are the same program. The hub keeps everything in one SQLite file, or in Postgres if you prefer.

Agents only reach out

They open no ports and run no commands. Each has its own credential, which you can revoke on its own.

Signed updates

Releases are signed. Agents update with a click, and install only what carries lotse's signature.

A read API

Everything you see is in a documented REST API, with read-only tokens and a Go client at lotse.sh/client.

Compared

Where lotse fits

Beszel and Uptime Kuma Two good tools, one for inside and one for outside. lotse does both in one place, and adds customers and projects, inherited settings, a history of changes, and configuration as code.
Checkmk, Zabbix They monitor nearly anything, and take an effort to match. lotse covers Linux machines, Docker and services from outside, and asks for nothing before it works.
Prometheus and Grafana A toolkit to build monitoring from. lotse is the finished thing: the charts, the checks and the alerts are there from the start.
